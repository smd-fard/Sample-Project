# implement-plan

Autonomous orchestrator. Reads `_design/<slug>/plan.md`, derives a task graph from the layered
architecture, embeds the relevant SKILL.md + templates into each spawned agent's prompt, enforces the
layer DAG with verification gates, and emits a final report. The main agent never writes production code —
all writes are delegated to subagents executing skill instructions with their own tools.

## Args

`<feature-slug>` — must match an existing `_design/<slug>/plan.md` (generated by `/define-plan`).

## Hard rules

- **Orchestrate; never implement.** The main agent does not write `src/` files — subagents do.
- **Layer ordering is non-negotiable.** A layer cannot start until the previous layer's gate (`npm run build`)
  passes. Enums/Models → DTOs → Contexts → Repositories → Services → Controllers → Tests.
- **Within a layer, tasks on disjoint files run in parallel** (multiple Agent calls in one turn). Tasks that
  share a file (e.g. several methods appended to the same `<Resource>Service.ts`) run sequentially.
- **Embed skill instructions; don't delegate via `/skill-name`.** Subagents have no Skill tool. Read each
  `.claude/skills/<skill>/SKILL.md` + every `@references/*` file and paste them verbatim into the prompt.
- **Verification gates are hard stops.** If a gate fails, halt, report with verbatim output, and stop.
- **No silent retry.** A failure means unexpected state needing human judgment.
- **Idempotency on re-invoke.** Before spawning an agent, check whether its primary output file exists; if so,
  mark the task done and skip.

## Plan → Skills mapping

| Plan language                                  | Skill             | Parallel?                                  |
|------------------------------------------------|-------------------|--------------------------------------------|
| enum / status / kind (fixed string set)        | define-enum       | Yes — disjoint files                       |
| model / entity / record                        | define-model      | Yes — disjoint files                       |
| DTO / request / response body                  | define-dto        | Yes across resources                       |
| context / call object                          | define-context    | Yes across resources                       |
| repository / data access / store              | define-repository | Yes across entities                        |
| service method / business logic                | define-service    | No — methods share `<Resource>Service.ts`  |
| controller / endpoint / route                  | define-controller | No — endpoints share `<Resource>Controller.ts` + `createApp()` |
| unit test                                      | write-unit-test   | Yes — sibling files                        |
| functional test / endpoint coverage            | write-functional-test | Yes — disjoint test files              |

## Steps

### Step 0. Preconditions
- `_design/<slug>/plan.md` must exist. If not: "Run `/define-plan` first."
- `_design/<slug>/spec.md` should exist (sanity check).

### Step 1. Parse plan + build task graph
Read `_design/<slug>/plan.md` and `spec.md` in full. Using the mapping table, derive a task list from each
bullet under Implementation Steps. For each task record: skill, args (`<resource> <verb>` / `<Entity>` /
`<Name>`), primary output file (for idempotency), layer, and parallelism. Check idempotency. Print the task
graph grouped by layer with the gate after each layer, then wait for the user to confirm ("yes", "go", "run it").

### Step 2. Cache skill content
Before spawning agents, read each referenced `SKILL.md` + all its `@references/*` files into context. Also
read the root `CLAUDE.md` — paste its Conventions section into prompts as the convention anchor (the
per-skill templates carry the concrete pattern).

### Step 3+. Execute layers in order
For each layer (Enums/Models → DTOs → Contexts → Repositories → Services → Controllers → Tests):

Spawn one Agent per task. Disjoint-file tasks go in parallel (multiple Agent calls in one turn); shared-file
tasks (services, controllers) go sequentially — wait for each `AGENT_SUCCESS` before the next. Each agent
prompt has three sections:

```
[TASK]
You are implementing part of the <slug> feature in the Sample-Project web server at <repo-root>.
Your single task: run the <skill> skill with args: <args>

[SKILL INSTRUCTIONS — execute exactly]
<full SKILL.md contents>

[TEMPLATES + CONVENTIONS]
<full @references/* contents> + the CLAUDE.md "Conventions" section

[DOMAIN CONTEXT — from plan.md]
<copy the bullet(s) describing this task's fields/behavior verbatim>

[COMPLETION PROTOCOL]
On success: output "AGENT_SUCCESS: <skill> <args>" + bullet list of files written.
On failure: output "AGENT_FAILURE: <error>" and stop.
Do NOT run npm build/test — the orchestrator runs the gate after the whole layer.
```

After each layer: run the gate `npm run build`. Halt on failure.

### Final. Test layer + full verification
Run the test-writing tasks, then the full gate:

```bash
npm run build
npm test
```

If anything fails, stop and report — do not fix in this skill.

### Report

```
Feature:  <slug>
Plan:     _design/<slug>/plan.md
Enums/Models: <n>   DTOs: <n>   Contexts: <n>   Repositories: <n>
Services: <n methods>   Controllers: <n endpoints>
Tests:    <n unit | n functional>
Verification: build ✓ | test ✓
Open items: <copy from plan.md>
```

## Failure report format

```
ORCHESTRATION HALTED
Layer:  <layer name>
Task:   <skill> <args>
Error:
<verbatim error output>

Completed: ✓ <task> ...
Remaining: · <task> ...

To resume: fix the issue, re-invoke /implement-plan <slug>. Tasks whose output files exist are skipped.
```
